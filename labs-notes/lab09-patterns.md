# ЛР 9. Шаблоны проектирования в агенте IntelligentTestAgent

Материал составлен по фактическому коду ветки `labs-agent`. Приложение написано на Kotlin (JVM), поэтому шаблоны выражены средствами Kotlin: интерфейсы, `sealed`-иерархии, `object`, лямбды-фабрики. Пути указаны от корня репозитория, пакет `com.example.agent`.

## 1. Назначение приложения

Агент принимает исходный код на Kotlin, разбирает его, подбирает входные данные по условиям в коде, выполняет функции, измеряет покрытие ветвей и записывает набор тестов JUnit 5 с проверками, полученными из реального запуска. Результат сохраняется в каталог артефактов и доступен через командную строку и REST API.

## 2. Сводная таблица шаблонов

| № | Шаблон | Тип | Где в коде | Зачем применён | Почему целесообразен |
|---|---|---|---|---|---|
| 1 | Facade (Фасад) | структурный | `api/PipelineService.kt`, класс `PipelineService`, метод `generateTests` | единая точка входа скрывает цепочку: загрузка, разбор, подбор значений, выполнение, кодогенерация, сохранение | CLI и REST используют один и тот же конвейер, клиенту не нужно знать порядок этапов |
| 2 | Strategy (Стратегия) | поведенческий | `source/SourceLoader.kt` (интерфейс `SourceLoader`), `LocalFileSourceLoader`, `source/GitSourceLoader.kt` | разные источники исходников за одним интерфейсом | добавление источника не меняет конвейер |
| 3 | Factory Method (Фабричный метод) | порождающий | `source/SourceLoaderFactory.kt`, метод `create` | по строке источника выбирает загрузчик: путь или адрес репозитория | выбор стратегии вынесен из конвейера, проверка адреса в одном месте |
| 4 | Observer (Наблюдатель) | поведенческий | `api/PipelineListener.kt` (интерфейс и события), рассылка в `PipelineService.notify` | этапы конвейера сообщают о ходе работы подписчикам | прогресс в консоли и история запусков подключаются без изменения конвейера |
| 5 | Strategy (стратегия кандидатов) | поведенческий | `coverage/CandidateStrategy.kt`: `CandidateStrategy`, `BoundaryVariationStrategy`, `HeuristicCandidateStrategy`, `CombinationStrategy` | разные способы порождать входные значения для функции | источники значений независимы, их набор задаётся снаружи |
| 6 | Strategy (стратегия мутаций) | поведенческий | `coverage/CandidateStrategy.kt` (`MutationStrategy`), `coverage/NeighbourhoodMutationStrategy.kt` | способ поиска значений для непокрытых ветвей | поиск можно заменить без правки генератора |
| 7 | Repository (Хранилище) | порождающий/архитектурный | `storage/RunRepository.kt`: `RunRepository`, `InMemoryRunRepository` | доступ к истории запусков через интерфейс | конвейер не знает, где хранится история (память, БД) |
| 8 | Bridge / Adapter (абстракция хранилища артефактов) | структурный | `storage/ArtifactStore.kt`, реализация `storage/ArtifactStorage.kt` | конвейер работает с интерфейсом, а не с файловой реализацией | хранилище артефактов заменяется, тесты подставляют своё |
| 9 | Sealed-иерархия результата (вариант Either/Result) | структурный | `execution/KotlinInMemoryCompiler.kt` (`CompilationResult`), `execution/TestCaseExecutor.kt` (`ExecutionOutcome`), `execution/TypeConversion.kt` (`ConversionResult`) | результат операции описан закрытым набором вариантов | компилятор проверяет обработку всех вариантов, ошибки не передаются исключениями |
| 10 | Singleton (Одиночка) | порождающий | `execution/TypeConversion.kt`, `object TypeConversion` | функции приведения типов без состояния | один экземпляр без состояния, не нужна синхронизация |
| 11 | Data Transfer Object | структурный | `api/dto/Dto.kt` | запросы и ответы REST отделены от внутренней модели | формат API не зависит от внутренних классов |
| 12 | Dependency Injection | принцип | `PipelineService`: параметры `listeners`, `sourceLoaderFactory`, `artifactStoreFactory` | зависимости передаются в конструктор | подмена в тестах, явные зависимости |


## 3. Подробности по ключевым шаблонам

### 3.1. Observer: события этапов

События (файл `api/PipelineListener.kt`): `AnalysisCompleted`, `FunctionProcessed`, `SuiteGenerated`, `ArtifactsSaved`, `PipelineCompleted`, `PipelineFailed`. Интерфейс `PipelineListener` содержит метод на каждое событие с пустой реализацией по умолчанию, поэтому подписчик реализует только нужные методы.

Рассылка (`PipelineService.notify`) оборачивает каждый вызов подписчика в `runCatching`: сбой наблюдателя не прерывает конвейер. Это проверяет тест `failing listener never breaks the pipeline`.

Реализации:
- `api/ConsoleProgressListener.kt` выводит ход работы в консоль, подключён в `Cli.kt`;
- `api/RunRecordingListener.kt` переводит события в `RunRecord` и сохраняет его через `RunRepository` (на следующем этапе работ репозиторий получает реализацию на SQLite).

### 3.2. Factory Method и Strategy для загрузки исходников

`SourceLoaderFactory.create(location)` возвращает `GitSourceLoader`, если разрешён удалённый доступ и строка похожа на адрес репозитория, иначе `LocalFileSourceLoader`. Проверка `isRemoteRepository` отвергает строки, начинающиеся с `-`, и пути, существующие на диске. `GitSourceLoader` дополнительно запускает `git clone` с разделителем `--`, чтобы адрес нельзя было принять за параметр.

Для REST удалённый доступ выключен по умолчанию (`allowRemote = false`): сервер не клонирует произвольные адреса. Командная строка включает его явно.

### 3.3. Strategy для кандидатов

До рефакторинга генерация значений была набором закрытых методов в `CoverageGuidedGenerator`. Теперь:
- `BoundaryVariationStrategy`: базовые векторы и замена одного параметра значениями вокруг порогов из условий;
- `HeuristicCandidateStrategy`: значения по типам параметров;
- `CombinationStrategy`: декартово произведение допустимых значений или случайные сочетания при большом числе вариантов;
- `NeighbourhoodMutationStrategy` реализует `MutationStrategy`: изменение значений соседними, умножение, деление, подстановка констант.

Генератор принимает список стратегий и стратегию мутаций в конструкторе (`candidateStrategies`, `mutationStrategy`). По умолчанию используется прежний набор, поэтому результат не изменился.

## 5. Что важно сказать на защите

- Шаблоны применены в уже существующем коде агента, а не в отдельном учебном примере.
- Поведение агента не менялось: это подтверждено сравнением покрытия и числа тестов.
- Язык проекта Kotlin; он компилируется в байт-код JVM и полностью совместим с платформой Java, которая указана в задании.
- Не все шаблоны нужны сразу: Observer и Repository подготавливают следующие работы (история запусков в базе данных и приложение над ней).
