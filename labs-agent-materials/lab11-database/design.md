# ЛР 11. Проектирование базы данных

## 1. Постановка задачи

Агент генерирует тесты для Kotlin-кода и после каждого запуска формирует три файла результатов (`analysis.json`, `test-cases.json`, `coverage.json`). Они перезаписываются или лежат в отдельных каталогах, поэтому нельзя сравнить запуски между собой и посмотреть динамику. Требуется база данных, которая хранит:

- проверяемые проекты и их исходные файлы;
- запуски генерации (время, длительность, статус, измерялось ли покрытие);
- функции, найденные в запуске, с цикломатической сложностью и числом ветвей;
- каждую ветвь с признаком покрытия (покрыта, не найдены значения, не инструментируется);
- тест-кейсы с видом сценария, источником значений, входными данными и ожидаемым результатом;
- пути к артефактам запуска.

Требования к базе: целостность на уровне СУБД (ключи и ограничения), третья нормальная форма, отсутствие серверной части (файл, который можно положить рядом с проектом), запросы для анализа: покрытие по запускам, самые сложные функции, непокрытые ветви, распределение кейсов.

## 2. Концептуальная модель

Сущности и связи:

| Сущность | Смысл | Связи |
|---|---|---|
| Проект | набор проверяемых исходников | имеет много файлов, много запусков |
| Исходный файл | файл `.kt` проекта | принадлежит проекту, содержит много функций |
| Запуск | одно выполнение агента | принадлежит проекту, имеет функции и артефакты |
| Функция | проанализированная функция в рамках запуска | принадлежит запуску, имеет ветви и тест-кейсы |
| Ветвь | точка ветвления функции | принадлежит функции |
| Тест-кейс | один сгенерированный сценарий | принадлежит функции, имеет вид и источник, имеет входные значения |
| Входное значение | значение параметра в тест-кейсе | принадлежит тест-кейсу |
| Артефакт | файл результата запуска | принадлежит запуску |

Связи «один ко многим» между всеми парами. Связь «функция, исходный файл» необязательная: файл может быть неизвестен при записи истории из конвейера без разбора путей.

## 3. Логическая модель и нормализация

### Первоначальный набросок и нарушения

Первая версия хранила всё в одной таблице `result(run_time, source_file, class, function, branch_label, branch_state, case_id, case_type, case_origin, input_x, input_y, ...)`.

Нарушения:

- **1НФ.** Входные значения лежали в отдельных столбцах `input_x`, `input_y`: число параметров у разных функций разное, часть столбцов пустая. Исправление: таблица `test_input(test_case_id, param_name, param_value)`.
- **2НФ.** `source_file` и `run_time` зависели только от части составного ключа (запуск, функция). Исправление: запуск и файл вынесены в `run` и `source_file`.
- **3НФ.** Вид сценария (`POSITIVE`, `NEGATIVE`, `BOUNDARY`) и источник значений хранились текстом в каждой строке, то есть значение `case_type` определяло само себя. Исправление: справочники `scenario_type` и `case_origin`, в `test_case` остались внешние ключи. Название проекта повторялось в каждой строке запуска, вынесено в `project`.

### Итоговые таблицы

| Таблица | Первичный ключ | Внешние ключи | Ограничения |
|---|---|---|---|
| `project` | `id` | | `name` UNIQUE |
| `source_file` | `id` | `project_id`, ON DELETE CASCADE | UNIQUE (проект, файл) |
| `run` | `id` (текст) | `project_id`, ON DELETE CASCADE | `status` IN (COMPLETED, FAILED), `duration_ms >= 0`, `coverage_measured` IN (0, 1) |
| `function_info` | `id` | `run_id` CASCADE, `source_file_id` SET NULL | `complexity >= 1`, `covered_branches <= total_branches`, UNIQUE (запуск, класс, функция, сигнатура) |
| `branch` | `id` | `function_id` CASCADE | `state` IN (COVERED, NOT_FOUND, NOT_INSTRUMENTABLE), UNIQUE (функция, код) |
| `test_case` | `id` | `function_id` CASCADE, `scenario_type_id`, `origin_id` | UNIQUE (функция, код) |
| `test_input` | `id` | `test_case_id` CASCADE | UNIQUE (кейс, параметр) |
| `artifact` | `id` | `run_id` CASCADE | `kind` IN (ANALYSIS, TEST_CASES, COVERAGE, TESTS_SOURCE), UNIQUE (запуск, вид) |
| `note` (добавлена в ЛР 12) | `id` | `run_id` CASCADE | `text` NOT NULL, CHECK (длина текста без пробелов > 0), индекс по (запуск, время) |
| `scenario_type` | `id` | | `name` IN (POSITIVE, NEGATIVE, BOUNDARY) |
| `case_origin` | `id` | | `name` IN (HEURISTIC, BOUNDARY, SEARCH) |

Идентификатор запуска текстовый, потому что агент создаёт его сам (UUID) до записи в базу. Остальные ключи целочисленные.

Источники значений соответствуют стратегиям подбора кандидатов в самом агенте: `HEURISTIC` (значения по типам), `BOUNDARY` (значения вокруг границ условий), `SEARCH` (поиск мутациями).

## 4. Физическая модель

Схема для SQLite лежит в `src/main/resources/db/schema.sql`. Решения:

- внешние ключи включаются командой `PRAGMA foreign_keys = ON` при каждом подключении (в SQLite по умолчанию выключены, агент и скрипты включают явно);
- индексы по полям, по которым идут соединения и отборы: `run(project_id, started_at)`, `function_info(run_id)`, `function_info(complexity)`, `branch(function_id, state)`, `test_case(function_id)`, `test_case(scenario_type_id)`, `test_input(test_case_id)`;
- представление `v_run_summary` собирает сводку запуска (функции, ветви, покрытые ветви) для запроса Q12;
- время хранится строкой в формате ISO 8601 в UTC (`2026-07-01T10:00:00Z`), чтобы сортировка по тексту совпадала с сортировкой по времени;
- справочники заполняются в самой схеме командами `INSERT OR IGNORE`.

## 5. Процесс создания и проверки

1. Схема написана в `schema.sql` и применена к пустой базе.
2. Агент запущен на трёх примерах (`OrderProcessor.kt`, `SampleCalculator.kt`, `SampleStringUtils.kt`), результаты загружены скриптом `create_database.py`. Данные реальные, не придуманные.
3. `verify_database.py` проверил целостность и внешние ключи, выполнил все запросы.
4. ER-диаграмма строится скриптом `make_er.py` по фактической структуре файла базы, то есть диаграмма не расходится с базой.
5. Запись истории включена в код агента (`SqliteRunRepository`, подписчик `RunRecordingListener`) и проверена тестами: сохранение и чтение, внешние ключи, каскадное удаление, сквозной запуск конвейера.

## 6. Ограничения

- Проверка значений в полях проводится ограничениями `CHECK` для перечислимых полей и для числовых границ. Ограничения на формат времени нет.
- Повторная загрузка тех же данных с тем же идентификатором запуска заменяет запуск целиком.
- Значения входных данных хранятся строками, как их создаёт агент (`"1"`, `"100.0"`, `"null"`).
