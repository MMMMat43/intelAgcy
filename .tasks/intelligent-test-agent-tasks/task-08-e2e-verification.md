# Task 08: Сквозная проверка и метрики

**Type:** Verification
**Suggested agent:** Test

## Goal
Провести сквозную (end-to-end) проверку всего конвейера на примере реального небольшого Java-файла/проекта: от загрузки исходников до сгенерированного JUnit5-кода тестов и сохранённых артефактов, убедиться в зелёной сборке, и задокументировать результаты в кратком отчёте с метриками.

## Why This Task Exists
Раздел "Выбор и подготовка тестового набора данных" и раздел 1.5 "Метрики оценки качества сгенерированных тестов" ПЗ требуют экспериментальной проверки решения на наборе программных проектов с оценкой по нескольким метрикам (структурное покрытие, распределение тестов по видам, трудозатраты). Эта задача — финальная верификация того, что реализованный в Tasks 01–07 пайплайн действительно работает целиком.

## Spec Coverage
- Requirements: R6
- Scenarios: S1, S2, S4

## Required Inputs
- Полный пайплайн из Tasks 01–07: `com.example.agent.source.SourceLoader`, `com.example.agent.analysis.JavaCodeAnalyzer`, `com.example.agent.generation.TestScenarioGenerator`, `com.example.agent.codegen.JUnit5TestCodeGenerator`, `com.example.agent.storage.ArtifactStorage`, REST API `com.example.agent.api` (эндпоинты `/analyze`, `/generate-tests`, `/health`).
- `Cli.kt` с флагами `--source`, `--generate-tests`, `--output` (из Tasks 01–06).

## Files/Areas
- `src/test/resources/` — добавить 1-2 небольших примера Java-файлов (`.java`) с ветвлениями, циклами, обработкой исключений разной сложности (например, `SampleCalculator.java` с методами деления/валидации и `SampleStringUtils.java` со строковыми проверками) — если такие файлы ещё не существуют.
- `src/test/kotlin/com/example/agent/e2e/` — новый end-to-end тест, прогоняющий полный пайплайн программно (не обязательно через HTTP, можно вызвать классы напрямую в правильном порядке) на подготовленных примерах.
- `.tasks/intelligent-test-agent-tasks/RESULTS.md` (новый файл в этой же task-папке) — итоговый отчёт с метриками.

## Constraints / Non-Goals
- Не требуется реальный запуск n8n или реального LLM API — сквозная проверка ведётся в fallback-режиме (без `LLM_API_KEY`), это допустимо и ожидаемо согласно Task 04/05.
- Не нужно проверять компиляцию сгенерированного `.kt`-файла в отдельном Gradle source set в рамках этой задачи — достаточно факта, что `JUnit5TestCodeGenerator` вернул непустой, синтаксически валидный (по проверке в Task 06) код, и что этот файл реально записан на диск через `ArtifactStorage`.
- Отчёт `RESULTS.md` — краткий (не более 1-2 страниц текста), с конкретными числами, не общими фразами.

## Output Artifacts
- `.tasks/intelligent-test-agent-tasks/RESULTS.md` — отчёт с метриками сквозного прогона.
- (при необходимости) `src/test/resources/*.java` — тестовые примеры для e2e-теста.

## What to Do
- Подготовить 1-2 примера Java-файлов с заведомо разнообразной логикой (минимум: один метод с if/else и циклом, один метод с обработкой исключений, один метод с числовыми и один со строковыми параметрами).
- Написать e2e-тест (`src/test/kotlin/com/example/agent/e2e/PipelineE2ETest.kt`), который:
  1. Загружает подготовленные примеры через `SourceLoader`.
  2. Прогоняет `JavaCodeAnalyzer` и проверяет, что получено ожидаемое количество функций.
  3. Прогоняет `TestScenarioGenerator` (без LLM ключа, в fallback-режиме) и проверяет, что для каждой функции сгенерирован минимум один сценарий каждого типа (`POSITIVE`, `NEGATIVE`, `BOUNDARY`), где это применимо по типам параметров.
  4. Прогоняет `JUnit5TestCodeGenerator` и `ArtifactStorage` (используя `@TempDir`) и проверяет, что артефакты реально записаны на диск.
- Запустить полную сборку и тесты проекта (`./gradlew build`, `./gradlew test`) и убедиться в успешном прохождении (зафиксировать факт в отчёте).
- Собрать метрики по результатам сквозного прогона на подготовленных примерах:
  - количество проанализированных функций;
  - средняя цикломатическая сложность по функциям;
  - количество сгенерированных тест-кейсов, разбивка по `ScenarioType` (POSITIVE/NEGATIVE/BOUNDARY);
  - время выполнения полного пайплайна на примерах (можно измерить простым `System.currentTimeMillis()` в e2e-тесте или логированием).
- Оформить `.tasks/intelligent-test-agent-tasks/RESULTS.md` с разделами: "Что проверено", "Метрики" (таблица с числами из предыдущего пункта), "Известные ограничения" (например, отсутствие реального LLM-ключа в проверке, отсутствие проверки компиляции сгенерированного кода отдельным сборочным шагом).

## Expected Output
- Прошедший e2e-тест в составе тестового набора проекта.
- Файл `RESULTS.md` с конкретными метриками.
- Подтверждение зелёной сборки (`./gradlew build`, `./gradlew test`).
